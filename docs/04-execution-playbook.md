# 单次任务执行与验收规程

## 你动手，我引导，不是让我一次性完成代码

每项任务采用如下流程：

1. **需求卡**：明确本次输入/输出、数据契约、权限、停止条件、至少两种失败边界和验收命令；只做一个有界能力。
2. **原理 + 源码（All-in-One）**：AI Agent Book 相应章节/官方实验，随后有针对性地对照 [Pi 源码](https://github.com/badlogic/pi-mono)；在聊天直接讲解必要代码和原理，未核实的源码路径要标注。
3. **软件设计原则**：从《软件设计的哲学》选择一个与本任务相关的原则（深模块/信息隐藏/复杂性/错误边界等），讨论何时适用及代价，不追加整门 CS190 课程。
4. **你的设计 + CS190 式评审**：你先画 Python 接口、数据流/状态与失败分支，并比较一个备选方案；我先以反例审查复杂性、边界、耦合、可测试性，而不是代你决策。
5. **Python 最小实现和测试**：你先写核心机制，ZCode/Matt Skills 做辅助；pytest Mock → 有条件的真实调用 → Golden Case，失败保留证据。
6. **Code Review / 按证据重构**：指出具体设计问题及可验证改进，避免为了使用设计模式强行拆模块。
7. **双重验收**：工程结果记录测试/Trace/成本/SHA；个人掌握独立解释、闭卷重建、变体、故障推理和取舍。2–4 道[小林 Coding](05-interview-map.md)真实原题 + 标明为改编的项目追问，T0/T+3/T+14 复核。
8. **归档与 Git 提交**：完成功能及真实验收证据才标工程通过；Notion Day 笔记允许自由记录、自答放在题后。不规定 Commit 数量。

## Git 原子提交准则

- 一次提交只承担一个变更意图；失败测试→实现→重构可以分别提交，但最终任务要有复现命令。
- 测试/README/ADR 跟随功能一起提交，避免“写完代码以后再一次性补文档”。
- `git status`、`git diff --check`、`python -m pytest` 在核心功能提交前执行；真实模型调用凭据只放本地 .env。
- 提交消息示例：`feat(runtime): close two-tool loop with typed results`，不强制出现 Cxx 课程编号。
- 每个完成的功能有 `docs/worklog/<date>-<slug>.md`，只记录已有**真实证据**。

## 统一完成定义（DoD）

- [ ] 需求与非目标明确，含输入/输出/失败条件
- [ ] 理解对应官方实验，能口述实际路径
- [ ] 自己画出数据流与函数契约，标记未知假设
- [ ] 正常、异常、边界测试真实执行过且通过
- [ ] 新功能经 Mock 运行；有外部依赖时完成真实冒烟或标待测
- [ ] 模型/Prompt/数据集版本、必要的 Trace/指标有记录
- [ ] Python 与 Agent/RAG 真实原题至少两道达到3/4分
- [ ] 代码可以被其他人按 README 复现；无密钥/个人隐私
- [ ] Git Commit SHA 与测试输出相对应

## 面试评分

0 完全不会；1 只背术语；2 能解释核心原理；3 能结合自己代码解释方案与取舍；4 能分析变体、失败与替代方案。Cumulative 题库中的一题过关不等于永久掌握，下一阶段抽样复核。

**强调**：小林 Python 官方118题是题库总量；我们优先学与 Agent 相关的核心题号，但没有证据说明这些题在牛客全站的精确出现次数。不要制造官方频次排名。

## 量化验收数据字典

| 字段 | 真实记录方式 | 不得做的事 |
|---|---|---|
| `case_id` `expected_action` | 人工审核需求/模拟资料 | 运行后偷改标签美化结果 |
| `model_id` `prompt_version` `dataset_version` | 原始配置+Git SHA | 只写“最新版模型” |
| `tool_calls` `tool_selection_correct` | 按已知意图与轨迹标注 | 把工具选择等同于工具执行 |
| `recall_at_5` | 被标注相关的来源进入 top5 比例 | 在不同数据集随意比较 |
| `citation_supported` | 人工逐事实验证引用支持 | 引用了链接就算正确 |
| `task_success` | 环境/工具结果确认目标完成 | 只凭语言评价/LLM 自评 |
| `latency_ms` `tokens` `cost_estimate` | 按提供商使用量、trace与计价记录 | 把模型估算当真实账单 |
| `failure_type` | 依赖/检索/工具/生成/权限/中断 | 吞掉失败，仅呈成功截图 |

初始 **3–5条** Golden Cases → RAG **10题** → 多组件 **20题+10安全/故障案例**是规划规模，未测不填分数。不要编造 QPS、真实用户数、性能提升或面试通过率。

## 资料与时间优先级

SalesPilot 业务 > AI Agent Book 最少充分原文与实验 > Pi 当次相关源码 >《软件设计的哲学》当次一个原则/CS190 设计审查 > AgentGuide 工程标准 > 小林相关真题。**这是同一次任务的不同视角，不是并行新增四门课**；每次最多 1 个核心实验 + 2–4 道题，其余以后再补。当前以 Python 练工程，Go 后期补。

论文为硬约束。以每周可用预算设上限，遇到论文/答辩紧急任务主动缩减 Agent 工时，不用频繁更换学习框架回避主任务。


## ZCode + Matt Skills 的两道独立门禁

开发方式详见 [AI 辅助学习防护协议](06-ai-learning-guardrails.md)。Matt Pocock 的 `teach`、`grill-with-docs`、`to-spec`、`to-tickets`、`tdd`、`implement`、`diagnosing-bugs`、`code-review`、`retro` 是可选择的执行工具，不是替用户自主设计的授权。

**工程验收**：真实运行的正常/异常测试、Mock 与必要的真实依赖检查、可复现命令、无泄密、Trace 和 Git SHA。允许功能通过而学习未通过。

**个人掌握验收**：脱离 ZCode/AI，不看生成的答案，依次核查：（1）解释模块目标和设计；（2）重建核心逻辑；（3）实现小幅变体；（4）从失败信息推理根因；（5）比较替代设计。逐项标通过/待补。五项均达标才能标“独立掌握”；未达标的功能可以交付但必须记“功能已实现，个人尚未掌握”。

**延迟保持检验**：T0 当天、T+3 天、T+14 天；时间允许时重复“闭卷重建+迁移”，不是照读笔记。重要面试能力以延迟检验结果为准。

**AI 编码授权等级**：核心首次学习只允许提示/审查/局部示范；通用工程可以让 AI 写但开发者审核；整份任务的 `implement-spec` / 自动并行实现须经明确授权，且不能作为独立能力证据。

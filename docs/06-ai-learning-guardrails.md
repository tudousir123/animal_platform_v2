# SalesPilot 人主导开发协议（ZCode + Matt Skills）

> **目标**：既借助 AI 高质量交付项目，也获得能在没有 AI 时独立设计、实现、排错和解释的工程能力。本文是学习/工程协作约束，不依赖特定插件自动强制执行。

## 决策权与实现权限

| 类型 | 例如 | AI 可以做 | 开发者必须做 |
|---|---|---|---|
| **首次学习的核心机制** | ModelClient、Tool Registry、Agent Loop、RAG、Context、async/取消、Eval设计 | 指教材、提出反例、局部示范、设计测试/Review | 独立画接口与状态、先写最小实现、解释失败与取舍 |
| **常规工程辅助** | 测试补充、Bug 定位、重构建议、文档和 API 设计评审 | 解释、审查、建议局部补丁 | 核对行为、复现证据、做最后决策 |
| **重复性工作** | 配置、样板、类型补全、常规脚本、文档格式 | 经授权可代写并验证 | 审核依赖与边界，能讲清代码行为 |
| **明确加速交付** | 重复性集成、大量简单页面、已掌握模块 | 经明确同意可用 `implement` 或 `implement-spec` | 标记 AI 主导的范围，不据此宣称独立掌握 |

**代码行数不是判断标准。** 验证的是需求判断、接口设计、故障推理、取舍和迁移能力是否属于开发者。

## 与 AI Agent Book / Pi / 软件设计的哲学的协同

每次任务由 AI Agent Book 提供必要原理与官方实验，由 Pi 源码提供定向设计对照（必须确认实际源码与版本），由《软件设计的哲学》提供 **一个当次相关的复杂性/模块化原则**。先由学习者独立设计，再按斯坦福 CS190 的“反例质询—修改设计—代码评审”循环改善方案。**CS190 不新增里程碑、不要求整书或全部课程前置。** 小林 Coding 原题验收仍须能结合本人 Python 代码和设计取舍回答。详情：[设计驱动学习协议](07-design-guided-learning.md)。

## 每个核心功能五道门禁

1. **独立构思**：读最小官方原文/实验，在不看 AI 实现的前提下，画出接口、数据流、状态、2 个失败分支。交付一页草图或短伪代码。
2. **设计质询**：使用 Matt `grill-with-docs`（必要时 `teach`）追问方案缺口，AI 先给问题与反例，不直接交完整实现。只有开发者确认后形成 Spec/ADR。
3. **亲自完成最小核心**：根据自己确定的行为边界和测试 seam，采用 `tdd` 红→绿、小步实现；AI 可以评审与解释测试，但不在学习模式下一键完成完整算法。
4. **故障推理**：出错后记录“现象→最可能原因→能证伪该原因的实验”。建议先尝试约20分钟，卡住再用 `diagnosing-bugs`；如果危险、重大损失或单纯环境故障，立即求助而非机械等待。
5. **闭卷验证**：暂时离开 AI 与生成代码，独立解释、重建、修改、调试并做架构取舍；结果留在学习记录。

## 双重验收的定义

**A. 工程门禁**：测试可复现、异常路径/边界覆盖、真实依赖未测如实标注、Trace/评测数据可信、代码无秘密、正常代码评审、Git SHA 记录。达标意味着「功能交付」，**不意味着个人掌握**。

**B. 学习门禁**：针对核心模块以下五项逐项留证据：

- **解释**：不看 AI 总结，说清目标、约束、模块职责及关键数据流。
- **重建**：在空白文件重写核心流程，或在规定时长内写出能验证的最小伪代码/代码。
- **迁移**：面对未练过的小变体，自己设计并修改，例如识别三次完全相同的工具调用。
- **调试**：仅给失败测试、日志/Trace，提出根因假设、验证和修复。
- **取舍**：解释所选方案与一种替代方案的性能、复杂度和失败模式。

五项都通过才标“独立掌握”，部分未通过标“功能已实现、个人待补”。**可将功能合并而不伪造掌握状态**；下一次优先安排针对性练习。

**间隔复核**：T0 当天 → T+3 天闭卷重建 → T+14 天新场景迁移。根据论文安排顺延可以，但要记录实际日期；没有做不能填写完成。

## Matt Pocock Skills 推荐组合

- **首次启动项目**：`setup-matt-pocock-skills` 配置问题跟踪、术语与文档位置；在 ZCode 能加载对应 Skill 的前提下调用。
- **读原理与学习记录**：`teach`，保留 `MISSION.md`、`learning-records/` 等学习产物；避免让它直接输出核心答案。
- **理解需求与设计**：`grill-with-docs` → `to-spec`，术语复杂时积累 `GLOSSARY.md`、架构取舍用 ADR。
- **任务拆分**：`to-tickets`，按可演示纵向切片与真实阻塞依赖拆，不规定固定 Commit 数量。
- **核心编码**：`tdd`，先共同选定 seam，由开发者写首个红测试与最小实现；AI 可提边界反例。
- **重复任务实施**：经批准使用 `implement`；首次学习的核心模块禁止默认交给 `implement-spec` 批量并行。
- **调试与代码审查**：`diagnosing-bugs`、`code-review`；必须解释症状、原因、验证证据与替代方案。
- **复盘**：`retro`，把反复出现的失误转成 lint、pytest、CI 或决策笔记，避免只有感想。

## ZCode 中可使用的开始任务提示词

> 这是 SalesPilot Learning Edition 的核心学习任务。请先读取 AGENTS.md、docs/04-execution-playbook.md 和 docs/06-ai-learning-guardrails.md。进入学习模式：只给本次业务需求、参考教材/官方实验入口、预期输入输出/失败边界和验收条件。先让我自己提交接口/状态图与伪代码；用反例质询，不提供完整代码。我的设计确认后，再共同确定测试 seam；按最小红绿循环实现。我写核心代码，你协助检查。完工后先做工程测试，再安排无 AI 的独立能力验收；两种结果分别记录在 docs/progress.md。

## 不适用的极端要求

不把“AI 写少于某个百分比”作为学习 KPI，不要求手抄框架样板，不以闭卷一时没写出所有语法为失败。衡量独立工程能力时，可以使用正常开发者合理查询的**官方文档**，但在指定闭卷测试中不得请求 AI 直接解题。遇到业务安全/隐私/密钥问题，及时停下求证。

**本协议约束的是使用方式，不保证 ZCode 自动识别已安装 Matt Skills。** 如果实际客户端对 Skills 的安装/引用机制不同，应按其官方兼容文档配置；不要宣称已安装。

# SalesPilot · 唯一有效的 Agent 实操教学协议（2026-10-10）

> **单一最新版本。** 本文是 M0–M5 的唯一实践、软件设计评审与 AI 辅助开发规范；里程碑见 [学习路线](03-learning-roadmap.md)，真实进度见 [progress](progress.md)。新增资料只改变当次实操，不得重新规划项目、堆叠课程或规定 Commit 数。

## 当前冻结范围

- **项目**：SalesPilot Learning Edition，面向新能源汽车销售顾问的知识问答、内网 RAG、网页搜索及有界研究；以 [产品规格](01-product-spec.md) 为准。**不是**角色扮演或销售训练评分系统。
- **开发语言**：Python 优先，自研最小 Agent Runtime，结合 pytest、FastAPI 等随能力引入；Go 放在项目完成初步验收后的补充阶段，不阻塞 M0–M5。
- **方法**：All-in-One，在聊天里讲理论、必要的关键代码与逐段解析，练设计、测试和面试；ZCode 负责编码辅助，但不代替学习者第一次完成核心设计。
- **阶段**：只保留 M0 需求基线 → M1 Agent/Tools → M2 RAG → M3 Web/研究 → M4 Session/API/SSE → M5 Eval/展示。任务与 Commit 数量根据依赖和真实证据自然生成。

## 一次功能任务：唯一执行流程（All-in-One）

1. **明确需求卡**：业务输入输出、核心契约、权限/停止条件、至少两个失败分支、非目标、最小可执行验收。
2. **理解原理和成熟实现**：看 AI Agent Book 指定正文/官方实验，按需阅读 Pi 对应源码；在对话里放教学化的短代码、注释、数据流和实验练习，明确引用与未验证部分。
3. **当次一个设计原则**：从复杂性、深模块、信息隐藏、通用/专用抽象、错误边界、战略编程中选一个；说明其何时适用、何时会过度设计。
4. **先由学习者独立设计**：提交接口、状态图/数据流、短伪代码、两个故障分支和一个替代设计。AI 做 CS190 式质询与反例，不提前给出完整核心答案；达成设计共识后可记 ADR/Spec。
5. **自己先写最小 Python 核心逻辑**：先确定测试接口（seam）和预期行为，pytest 做真实红→绿；AI 可写重复性脚手架/给局部样例，但未经专门授权不得首次一键实现 Agent Loop、Tool Registry、RAG、Context、async 等核心能力。
6. **验证和 Code Review**：跑 Mock/pytest、边界与错误路径、Golden Cases；有条件做真实依赖冒烟并保留去敏 Trace。审查模块职责、接口深浅、信息隐藏、耦合、认知负担、错误传播、可测试性；对有证据的问题小步重构，不为套模式重构。
7. **双重验收**：工程门禁与个人掌握分开。工程门禁记录测试命令/输出、Golden Case、Trace、实际依赖验证、Commit SHA；学习门禁需**独立解释、闭卷重建、迁移变体、定位故障、比较设计取舍**。使用小林原题 + 现场追问，T0/T+3/T+14 复核；未执行不得标通过。
8. **归档**：GitHub 存代码、可复现实验、技术决策和状态；Notion Day 页面让学习者自由记录思考、答案，不预设固定笔记模板。完成实际功能才提交成果，不追逐 Commit 次数。

## 工程与个人掌握两道独立门禁

**工程门禁（DoD）**
- [ ] 需求、非目标、输入输出、错误边界清楚
- [ ] 能解释对照过的官方实验和本人设计的数据流
- [ ] 正常/异常/边界测试实际运行；用例及结果可复现
- [ ] 真实服务依赖测过就记证据，未测明确“待测”
- [ ] 记录所用模型/Prompt/数据版本及必要的去敏 Trace
- [ ] 未提交凭据、隐私或无授权第三方题库/源码
- [ ] README 复现命令及 Commit SHA 与测试结果对应

**个人掌握门禁**：不看 AI 总结、直接依据本人代码完成五项：解释 → 重建 → 迁移 → 调试 → 取舍。可使用普通开发时合法的官方文档；闭卷指定环节不能用 AI 直接回答。五项有证据才记“独立掌握”，不足则标记“功能已实现，个人待补”。

**面试评分**：0=不会；1=术语；2=原理；3=能关联自己代码与理由；4=能分析变体/异常/替代。相关题至少达到 3/4 分；再次抽检保持率。所谓“小林原题”必须有来源链接，改编题不要冒充原题，也不要虚构牛客高频排名。

**证据口径**：任务是否成功必须由实际运行与工具结果确认，不能以模型声称成功代替；召回率填真实分子/分母；真实延迟和成本应来自 Trace 与计量；没有测量不填数字。Golden Case 从 M0 逐步增长，而非规划题数即结果。

## ZCode + Matt Skills：授权与排错边界

| 工作类型 | AI 可以做 | 本人必须做 |
|---|---|---|
| 第一次学的核心机制 | 讲理论、局部示范、反例质询、测试建议和 Review | 定义接口/状态、独立最小实现、故障推理 |
| 常规工程辅助 | 文档、样板、类型提示、重复测试、部分配置 | 审核输出、确认依赖和行为 |
| 明确授权的快速交付 | implement / 生成重复性实现 | 记录 AI 负责的范围，不把它当作“自己已掌握”的证据 |

- 可按当前需要组合 Matt Skills：teach → grill-with-docs → to-spec / to-tickets → tdd → code-review → diagnosing-bugs → retro。仅在 ZCode 实际支持且已加载时使用，不能虚构成功安装。
- Debug 时先描述“现象 → 根因假设 → 如何证伪”。通常可自己尝试约 20 分钟后寻求工具帮助；安全、数据损失、环境故障时立即处理，不机械等待。
- 禁止以 AI 编写代码占比作为 KPI；也不需要手抄样板。**原则是核心判断属于你，重复劳动可交给 AI。**
- 本任务默认阅读不超过一个核心实验、一个设计原则、2–4 道面试题。毕业论文优先；没有理由新增平行课程、过多工具和重型依赖。

## M0–M5 对应的软件设计观察点

| 阶段 | 当次可选原则 | 问自己的问题 |
|---|---|---|
| M0 需求/基线 | 复杂性、职责边界 | 哪些业务不用自主 Agent？ |
| M1 Tool/Agent Loop | 深模块、信息隐藏、错误边界 | 谁声明 Schema，谁验证参数，谁决定权限并执行工具？ |
| M2 RAG | 抽象边界 | 检索细节是否泄露给 Runtime？ |
| M3 Web / 研究 | 失败和不可信输入隔离 | 搜索失败、网页注入与模型决策如何隔离？ |
| M4 Session/API/SSE | 依赖方向、状态生命周期 | HTTP、Session、Runtime 之间怎样保持低耦合？ |
| M5 Eval/优化 | 战略编程、可证实的重构 | 哪次改动有证据降低认知或变更成本？ |

## 当前教学实例：Tool Schema / 参数校验 / 执行边界

需求：模型申请调用某个工具；宿主检查是否存在、参数能否通过 Schema、权限是否允许、是否超时，并将真实 ToolResult 按 call ID 交还上下文。由学习者先设计 ToolSpec、Registry、Executor、Agent Loop 职责，注意拆分过细也会增加复杂性。用 Python Mock 证明成功、非法 JSON、未知工具、无权限、执行故障、重复调用和最大步数等分支；再按 Pi 实际源码进行设计对照，并用小林工具调用题验收。
